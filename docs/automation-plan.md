# خطة أتمتة — خط إنتاج ملفات PDF (pdf-gold-standard)

> مطبَّقة وفق منهجية «دليل الأتمتة» (أكاديمية طويق — الإصدار الثامن):
> بوابة الاختيار → تحليل سير العمل → التصميم → الحوكمة → الإطلاق التدريجي.
> المالك المسؤول: م. عبدالرحمن جحفلي · التاريخ: ١٣ سبتمبر ٢٠٢٦

## ١) المرشح

- **العملية:** دورة إنتاج وتسليم ملف PDF بالمعيار — من مصدر HTML مصمم، عبر الفن والبناء والتحقق، إلى ملف منشور ورابط دائم.
- **المالك:** م. عبدالرحمن جحفلي (قرارات الإخراج والقبول النهائي).
- **النطاق:** من push للمصدر → ملف PDF متحقق منشور.
- **التكرار:** كل وثيقة وكل إصدار (v1 · v2 · الوثائق القادمة).
- **الألم الحالي:** البناء والنشر يدويان على جهاز واحد؛ خطر أن يشير الرابط لنسخة قديمة؛ خطوات متكررة تأكل الوقت.

## ٢) بوابة المعايير (١ = ضعيف · ٥ = قوي)

| المعيار | النتيجة | الدليل |
|---|---|---|
| تكرار وحجم | ٤ | كل وثيقة تمر بنفس السلسلة السبعية |
| وضوح القواعد | ٥ | `build.py` يحدد السلسلة كاملة — حتمي |
| قابلية التنبؤ | ٥ | نفس المدخلات → نفس المخرج (خطوط وفن مدمجان) |
| وضوح المدخلات/المخرجات | ٥ | مدخل: HTML + embeds + fonts · مخرج: PDF بمواصفة مقيسة |
| جودة البيانات | ٥ | كل المصادر في Git؛ لا مدخلات يدوية عشوائية |
| التكامل | ٥ | Actions + Chrome headless + Python — كله جاهز |
| ROI | ٥ | التكلفة: ملف workflow واحد · العائد: إزالة ~٢٠ دقيقة يدوية/إصدار + صفر «رابط قديم» + بوابة تحقق إلزامية |

**القرار:** اجتاز البوابة — لا معيار ≤ ٢، و ROI = ٥ → ننتقل للتحليل ثم التصميم.

## ٤) نقاط الاختناق المحددة

1. **النشر اليدوي (٧):** كل إصدار معلّق على تذكّر البشر — وأي نسيان يترك الرابط العام قديماً.
2. **البناء المركزي (٣):** جهاز واحد · لا أثر تدقيق مركزي لكل بناء.
3. **التحقق المتفرق (٤):** بنود التحقق تعيش في الذاكرة لا في ملف قابل للتشغيل داخل البوابة.

## ٥) قرارات التصميم

- **النوع/الدرجة:** «أتمتة عمليات» قائمة (سكربتات) → ترقية منصّبية مدمجة: **GitHub Actions**.
  *ولماذا ليس درجة أعلى (RPA / ذكاء اصطناعي)؟* لا حاجة لقيادة واجهات — الأنظمة CLI/API أصلاً —
  ولا حاجة لحكم بالبيانات في خط البناء؛ أضعف درجة تحل المسألة هي الصحيحة، والأعلى مؤجلة حتى تبررها الحاجة.
- **الطبقة:** مدمجة في منصّة الاستضافة (Actions) — بلا مزوّد جديد · الصيانة: المالك.
- **نقاط الإنسان في الحلقة:** توليد الفن (تكلفة + إبداع) · القبول البصري النهائي · أي تغيير تصميمي — لا أتمتة للحكم الجمالي.
- **خط الرجوع:** `git revert` للـworkflow · مخرجات مؤرشفة لكل تشغيل (artifact) · الإصدارات ثابتة → إعادة بناء وإصدار جديد.

## ٦) الحوكمة — العناصر العشرة

1. **الأهداف والأدوار:** الهدف: كل push يُنتج ملفاً متحققاً · الأدوار: المالك (مُقرِّر) · CI (منفّذ) · مزوّد الفن (مورّد خارجي).
2. **سياسة البيانات:** المستودع عام (MIT) · **سر التصميم: البناء لا يحتاج أي مفاتيح** (الخطوط والفن embeds داخل الريبو) — مفتاح OpenRouter لا يدخل Actions إطلاقاً، يبقى محلياً لتوليد الفن فقط.
3. **إدارة المخاطر:** فشل البناء → CI أحمر مرئي (لا انحراف صامت) · انحراف أدوات → نطاقات إصدار مثبتة · تبعية Chrome → runner رسمي.
4. **التدقيق والامتثال:** سجل تشغيلات Actions أثر تدقيق لكل بناء · الخطوط OFL مضمّنة برخصها.
5. **أدوات المراقبة:** شارة الحالة في README + تاريخ التشغيلات + إشعار بريدي عند الفشل.
6. **الشفافية:** لا قرارات AI داخل البناء (حتمي بالكامل) · الفن المولّد يمر بمراجعة بشرية قبل الدمج.
7. **الخصوصية:** لا بيانات شخصية في خط البناء · المفاتيح خارج المستودع.
8. **العدالة/التحيز:** لا قرارات على أفراد — غير منطبق · الفن إبداعي مراجَع.
9. **المساءلة:** الفشل يظهر في اللوحة ويُعالج بـcommit إصلاحي — مسؤولية المشروع للمالك.
10. **إدارة التغيير:** مراجعة عند ترقية أدوات كبرى · دورية مراجعة شهرية + عند فشل متكرر.

## ٧) مؤشرات النجاح (KPI)

| المؤشر | خط الأساس | الهدف |
|---|---|---|
| وقت البناء + النشر | يدوي ~١٥–٢٠ دقيقة/إصدار | ≤ ٥ دقائق آلية على كل push |
| خطوات يدوية/إصدار | ٧ من ٧ | ٢–٣ (تصميم + فن + قبول) |
| خطر «الرابط القديم» | قائم | صفر — أرتيفاكت لكل push |
| بوابة التحقق | متفرقة | `scripts/verify_pdf.py` إلزامية (12ص · 42 رابطاً · SinglePage · خطوط مدمجة) |

- **دورية المراجعة:** شهرية + عند أي فشل متكرر · **مُطلِق التحديث:** تغيير في سلسلة الأدوات أو بنية الريبو.

## ٨) الإطلاق التدريجي المنفَّذ

1. **المرحلة ١ (نُفِّذت):** workflow «Build PDF» — بناء + بوابة تحقق + أرتيفاكت على كل push.
2. **المرحلة ٢ (مضمّنة):** إصدار آلي عند وسم `v*` مع رفع الملف — الرابط الدائم يتحدث بنفسه.
3. **المرحلة ٣ (لاحقاً):** نظام الثيمات `--theme` ثم جسر LangChain — ترقية لدرجة الذكاء عند نمو الحجم.

## ٩) إثبات البوابات

- بوابة الاختيار: جدول القسم ٢ (تقييمات + قرار).
- أداة البوابة الجديدة: `scripts/verify_pdf.py` — نفس بوابة CI، قابلة للتشغيل محلياً.
- أول تشغيل: تبويب **Actions** بالمستودع (build-pdf).
