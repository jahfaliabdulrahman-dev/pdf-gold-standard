# خطة دمج التشكيل في مسار الحقول

## المكان المحدد (بالمصدر لا بالتخمين)

`core/fpdfdoc/cpdf_generateap.cpp`:

| السطر | ما يفعله | العيب |
|---|---|---|
| `:60` | `GetPDFWordString(font_map, font_index, word, ...)` | يترجم كل **حرف يونيكود** إلى `char_code` منفرد |
| `:83` | `pdf_font->CharCodeFromUnicode(word)` | لا يعرف التراكب: «لا» حرفان ⇒ رقمان |
| `:85` | `pdf_font->AppendChar(&word_string, char_code)` | يُلحق كل رمز على حدة ⇒ بلا تشكيل |
| `:315` | `GenerateEditAP(...)` | يبني الـAP من السلاسل أعلاه |

**الخلاصة**: الحقل يُرسم بترجمة حرف↔رمز، لا بتشكيل. لا وجود لـHarfBuzz في هذا المسار إطلاقًا.

## التصميم المقترح

1. **قبل** `GetPDFWordString`: شكّل الكلمة بـ`ShapeUtf16` مستخدمًا **الخط الأصلي الكامل** (لا المضمَّن —
   قياس: المضمَّن مجموعة فرعية بلا `cmap`، فكل المعرّفات صفر).
2. حوّل `glyph id → char_code` المطلوب للخط:
   - إن كان الخط `Identity-H` و`CIDToGIDMap = Identity` ⇒ `char_code = glyph id` مباشرة.
   - وإلا ⇒ جدول `glyph id → CID` من `CIDToGIDMap` المضمَّن (عكسه).
3. ألحق الرموز **بترتيب التشكيل** مع `Td` لكل محرف (نفس ما أثبتناه: صفر فرق بكسل).
4. عند غياب الخط الكامل أو غياب الغلاف (coverage) ⇒ **الرجوع للسلوك القديم** لا الفشل.

## القيود المقاسة

- الخط المضمَّن في PDF مجموعة فرعية بلا `cmap` ⇒ التشكيل به مستحيل (٠ معرّفات).
- `CharCodeFromUnicode` لا يصلح للتراكيب: لا يونيكود للكشيدة/اللام-ألف الناتجة عن التشكيل.
- كل دورة بناء PDFium ≈ ١٠ دقائق ⇒ التعديل يجب أن يُختبر أولًا خارج الشجرة.

## ما لم يُثبت بعد
- أن PDFium يقبل `CIDToGIDMap` العكسي في كل أنواع الخطوط المضمَّنة.
- أن الحقول ذات الخطوط القياسية (Helvetica) قابلة للإصلاح أصلًا (لا تغطية عربية).
