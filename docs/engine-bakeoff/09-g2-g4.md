## 2 · G#2 — veraPDF UA-1 `7.2-43`: an empty cell must keep its column

**Rule** (veraPDF 1.30.0, ISO 14289-1:2014 profile): *“Table rows shall have the same number of columns (taking
into account column spans)”*. On the old `tbl-empty-cell.pdf` veraPDF said: *“Table rows 1 and 2 span different
number of columns (3 and 2 respectively)”*.

**Cause, measured:** Chrome drops a `<td></td>` with no content from the structure tree. The raw `chrome-raw`
file already has rows `[3,2,2]` — this is the producer, not our postprocess. A cell containing one non-breaking
space keeps its `/TD` (measured on a six-row variant: empty → 2 cells; `&#160;` → 3; `<span></span>` → 2; `<br>` →
2; `<span>&#160;</span>` → 3).

**Fix:** `conformance/adapters/html.py::_cell` writes `&#160;` for an empty **or whitespace-only** cell
(`not text.strip()`). U+00A0 is whitespace: `metrics.N` collapses it, so it adds no word and no token; the text
layer is unchanged in words, and the table has three cells in every row.

**Witness:** `conformance/tests/test_engine_behaviour.py` now asserts the HTML (`_cell(“”) == _cell(“  ”) ==
“&#160;”`), the structure rows (`[3,3,3]`), `tables` pass, and `verapdf-ua1` pass (no failing rule). Remove the
space and the rows go back to `3,2,2`; the test fails.

**Production rule, stated:** the corpus renderer writes the space automatically; a hand-authored document (F's
template included) must write `&#160;` in an empty cell of its source HTML. The gate's `tables` check fails any
file whose row lost a cell, so the rule has a gate behind it — the fix is at the producer, not a second tagger
patched onto Chrome's tree.

**Scope note:** an empty `/TD` inserted into the structure tree by hand also makes UA-1 pass (measured), but it
needs the cell's x position to land in the right column, and a wrong guess links the cell to the wrong header.
That is a second producer beside Chrome's; it is not used.

## 3 · G#4 — numerals

**Owner decision (19 Nov 2026):** Western digits (`0-9`) are the default; Arabic-Indic (`٠-٩`) is an explicit
per-document choice, never derived from the locale; identifiers (VAT, CR, IBAN, invoice number, phone) and
XML/QR stay Western.

**Two generic checks in the certificate gate** (`conformance/checks/structure.py`, every certified file):

- `numerals-persian` — no U+06F0–U+06F9 digit anywhere in the text layer. A Persian digit is never an Arabic
  document's digit; the `lang` check already fails a file that is not `ar`, so this check is unconditional and
  does not add a second, coupled reason to fail.
- `numerals-mixed` — one number never mixes digit systems. A number is a maximal run of digits plus the
  separators that bind one number: `. , ٬ ٫`; ASCII/`arab`/`persian` digits inside one token fail. A hyphen,
  slash or space ends the token (`2026-11-19` is three numbers; a phone written with spaces is several).
  **Separator style alone is not a mix**: `1٬200` has one numeral system and passes; the owner's decision names
  numerals and identifiers, not separators, and the corpus case for identifiers tests the identifier rule.

**Two selftest mutations** (`conformance/selftest.py`, 17 total now): a drawn digit's `/ToUnicode` is mapped to
U+06F1 → `numerals-persian` fails; one digit of an ASCII number is mapped to U+0661 → `numerals-mixed` fails.
The drawn glyph does not change, so the mutation is a change of the **claimed** text. Both CAUGHT, 0 missed.

**Four corpus cases** (the owner's list):

| id | content | proves |
|---|---|---|
| `num-invoice-latn` | `الإجمالي: 1,200.00 ريال.` + VAT/CR/invoice identifiers, Western | the F default; Preview reads it correctly |
| `num-invoice-arab` | `الإجمالي: ١٬٢٠٠٫٠٠ ريال.` | the explicit Arabic-Indic option (the known Preview separator class, recorded not hidden) |
| `num-ids-latn-in-arab` | VAT, CR, IBAN, invoice, phone — all Western — each on its own line, plus an Arabic-Indic amount | identifiers stay Western inside an Arabic document; direction does not follow the paragraph |
| `num-negative-arab` | `المبلغ: -١٬٢٠٠٫٠٠ ريال.` | a negative Arabic-Indic amount mid-line (the line-start twin is the first case above) |

All four pass the certificate gate (20 checks each, including the two new ones and veraPDF). `num-invoice-arab`
and `num-negative-arab` are expected to fail **Preview** on the Arabic separators — that is the G#1b class,
recorded here as a reading, not turned into a passing claim.

**Unit control:** `conformance/tests/test_certificate.py` control 11 pins the tokenizer edges (ASCII, Arabic,
mixed across a separator, hyphen/space boundaries, IBAN, phone, Persian-only). The last one is deliberate:
`numerals-mixed` does not judge a Persian-only number — `numerals-persian` does.

## 6 · Ratchet integrity (found by the consultation, fixed here)

`ratchet.accept` used to replace every case's block with the run's values, so an `--accept` after a regression
rewrote the floor to the regression. It now **refuses** any run that lowers a metric or raises a defect count;
`--force` is the explicit rebase. `conformance/tests/test_ratchet.py` proves the refusal (and that the file is
unchanged), the defect-count refusal, and the forced path.
