## 2 · G#2 — veraPDF UA-1 `7.2-43`: an empty cell must keep its column

**Rule** (veraPDF 1.30.0, ISO 14289-1:2014 profile): *“Table rows shall have the same number of columns (taking
into account column spans)”*. On the old `tbl-empty-cell.pdf` veraPDF said: *“Table rows 1 and 2 span different
number of columns (3 and 2 respectively)”*.

**Cause, measured:** Chrome drops a `<td></td>` with no content from the structure tree. The pre-fix G#1b build
(`docs/conformance/results/2026-11-19-g1b-chrome.md`, case `tbl-empty-cell`) has rows `[3,2,2]`; the test
`conformance/tests/test_engine_behaviour.py` now renders the same case with `_cell` forced to return `""` and
asserts `[3,2,2]`, `tables` fail, and `verapdf-ua1` fail (`7.2-43`). The fixed build has `[3,3,3]` and both
pass. A cell containing one non-breaking space keeps its `/TD`.

**Fix:** `conformance/adapters/html.py::_cell` writes `&#160;` for a cell with **no character of substance**
(empty, whitespace-only, or only format controls such as RLM/ZWSP). U+00A0 is whitespace: `metrics.N` collapses
it, so it adds no word and no token; the text layer is unchanged in words, and the table has three cells in every
row.

**Witness:** `conformance/tests/test_engine_behaviour.py` asserts the HTML (empty, whitespace-only and
format-only cells become `&#160;`), the **defect half** (with `_cell` forced to return `""`, the same case has
rows `[3,2,2]`, `tables` fails and `verapdf-ua1` fails), and the fixed half (rows `[3,3,3]`, `tables`,
`verapdf-ua1`, `tagged-text` and `all-text-tagged` pass). Remove the space and the rows go back to `3,2,2`; the
test fails.

**Production rule, stated:** the corpus renderer writes the space automatically; a hand-authored document (F's
template included) must write `&#160;` in an empty cell of its source HTML. The gate's `tables` check fails any
file whose row lost a cell, so the rule has a gate behind it — the fix is at the producer, not a second tagger
patched onto Chrome's tree.

**Scope note:** an empty `/TD` inserted into the structure tree by hand also makes UA-1 pass (measured), but it
needs the cell's x position to land in the right column, and a wrong guess links the cell to the wrong header.
That is a second producer beside Chrome's; it is not used.

## 3 · G#4 — numerals

**Owner decision (19 Nov 2026):** Western digits (`0-9`) are the default; Arabic-Indic (`٠-٩`) is an explicit
per-document choice, never derived from the locale; identifiers (VAT, CR, IBAN, invoice number, phone) and
XML/QR stay Western.

**Two generic checks in the certificate gate** (`conformance/checks/structure.py`, every certified file):

- `numerals-persian` — no U+06F0–U+06F9 digit anywhere in the text layer. A Persian digit is never an Arabic
  document's digit; the `lang` check already fails a file that is not `ar`, so this check is unconditional and
  does not add a second, coupled reason to fail.
- `numerals-mixed` — one number never mixes digit systems. A number is a maximal run of digits plus the
  separators that bind one number: `. , ٬ ٫`; ASCII/`arab`/`persian` digits inside one token fail. A hyphen,
  slash or space ends the token (`2026-11-19` is three numbers; a phone written with spaces is several).
  **Separator style alone is not a mix**: `1٬200` has one numeral system and passes; the owner's decision names
  numerals and identifiers, not separators, and the corpus case for identifiers tests the identifier rule.

- **Persian is literal:** `numerals-persian` fails any U+06F0–U+06F9 in the layer, including a Persian numeral a
  document *quotes* (e.g. a Persian price). The owner's rule is absolute; a quote exception is a future decision,
  not a silent carve-out. `numerals-mixed` ignores Persian, so one Persian digit is reported by one check only.
- **The `numerals` field is F's, not G#4's:** the owner's routing puts `numerals: latn|arab` in
  `render_document` (and the identifiers rule) on the F task. G#4 adds the two universal gate checks and the
  corpus cases; the case files carry the choice in their text, not in a schema field yet.

**Two selftest mutations** (`conformance/selftest.py`, 17 total now): a drawn digit's `/ToUnicode` is mapped to
U+06F1 → `numerals-persian` fails; one digit of an ASCII number is mapped to U+0661 → `numerals-mixed` fails.
The drawn glyph does not change, so the mutation is a change of the **claimed** text. Both CAUGHT, 0 missed. The
limit is declared: a producer that draws a Persian glyph and maps it to ASCII is not caught by these checks
(ToUnicode is the claim); `tounicode-coverage` only checks presence.

class. The corpus is a bake-off: a case is a measurement, not a promise that every reader passes.

**Unit control:** `conformance/tests/test_certificate.py` control 11 pins the tokenizer edges (ASCII, Arabic,
mixed across a separator, hyphen/space boundaries, IBAN, phone, Persian-only, Persian+ASCII). The last two are
deliberate: `numerals-mixed` does not judge Persian — `numerals-persian` does.

## 6 · Ratchet integrity (found by the consultation, fixed here)

`ratchet.accept` used to replace every case's block with the run's values, so an `--accept` after a regression
rewrote the floor to the regression, and a **partial** run (the documented `--cases` path) erased the cases it did
not measure. It now **refuses** a run that lowers a metric, raises a defect count, drops a recorded case, or
loses a defect kind; `--force` is the explicit rebase and prints what it lowered. The write is atomic
(`.tmp` + `os.replace`), and a mixed-shape file is refused by name instead of being replaced. `test_ratchet.py`
proves the refusals leave the file unchanged and that the forced path writes.
